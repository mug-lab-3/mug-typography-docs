LUA SCRIPTING API

API Reference

The complete specification of the callbacks, ctx objects, coordinate systems, and mt.* utilities available to Mug Typography Lua scripts.

Also available offline

Target audience: Users creating animations with Mug Typography's scripting features API level: 6

Mug Typography scripting is a feature for controlling text layout and Character/Part animations with Lua 5.4 scripts written in the plugin's Script Text. For development, you can use the VS Code extension “Mug Typography Scripting Simulator” (MT Sim) and the installation-free online simulator available in a browser. Both let you preview and debug scripts without launching the host application.

1. Basic Model ​

A script can define up to four callback functions. All are optional, and callbacks that are not defined are simply skipped.

text
Initialization path (once when the script is loaded)

  Script loading
    └─ OnInitialize(ctx)
         Run for compatibility with existing scripts


Frame evaluation path (every frame)

  Every frame
    └─ OnPreLayout(ctx)
         Modify base values for layout, Global settings, and camera
          ↓
       Generate Character and Part layout
          ↓
       OnLayout(ctx)
         Individually adjust the generated Characters and Parts
          ↓
       OnPath(ctx)
         Adjust the outlines of selected Parts
          ↓
       Rendering

The important point is that the execution timing and the objects that can be manipulated differ for each callback. Define only the callbacks for the stages appropriate to your purpose.

  • OnInitialize is retained for compatibility with existing scripts. Do not define it in new scripts
  • OnPreLayout runs before layout generation on every frame. It changes the generation conditions for Characters and Parts, such as text, font, tracking, Global settings, and camera
  • OnLayout runs after Characters and Parts have been generated. It adjusts the position, rotation, color, and other properties of each generated element
  • OnPath runs after individual adjustments and before rendering. It replaces or rebuilds the outlines of selected Parts

Later callbacks can read values finalized in earlier stages. However, they cannot go back and rewrite values in a stage that has already been processed. For example, OnLayout can read ctx.global and ctx.camera, but cannot modify them.

Changes Are Valid Only Within the Frame ​

Every frame, ctx is passed to callbacks as state recreated from the host's Inspector values. Values written by callbacks are used only to render that frame, and the next frame starts again from the Inspector values. They are never written back to the Inspector or keyframes.

For example, ctx.global.rotation = ctx.global.rotation + 1.0 does not mean “continue rotating by one degree every frame”; it means “always use the Inspector value + 1 degree.” To advance the rotation, calculate the current angle directly from ctx.time, as in ctx.global.rotation = ctx.time * 20.0.

2. Frame Independence Requirement (Stateless Execution) ​

The host does not necessarily evaluate frames in chronological order. The result must be the same during scrubbing, reverse playback, caching, and parallel rendering. The result of each frame must be determined only by the current input values and must not depend on the previous frame's result or the order in which frames are evaluated. In this document, this property is called frame independence.

  • If you modify a global variable or a local variable declared outside a function, do so only to pass a value between callbacks within the same frame, and overwrite it from the current input values on every frame. Do not carry forward or accumulate values from the previous frame
  • Do not retain references such as ctx or ctx.chars[index] after the callback ends
  • Do not assume fixed values for the character count, Part count, or the shape of a particular font
  • Derive the value for the frame directly from ctx.time instead of using a sequential simulation
  • Always use ctx.char_count / ctx.part_count when iterating over Characters or Parts

Placement and Parsing Range ​

@duration / @required / @recommend / @title / @author / @version / @api_level are parsed only within the run of consecutive single-line comments starting at the @MugTypography line. The parsing range ends when an @description block comment or a line that is not a comment (including a blank line) is reached. Therefore, write single-line metadata before @description. Multiple @recommend lines and multiple settings on one line are both supported. In generated code, put the identification comment on line 1 and the other metadata and description immediately after it.

TIP

Design rule for scale adjustment: For Global size adjustments based on text length or character count, such as preventing content from extending off screen, adjust ctx.global.scale in advance during the OnPreLayout phase instead of dynamically reducing each Character's character.scale in OnLayout. This prevents the overall scale from changing in real time and jittering as the character count increases or decreases during animations that gradually add Characters, such as a typewriter effect.

See ctx.timeline for time-axis design rules (real seconds vs. progress).

3.5 Complete Script Example ​

lua
-- Base phase: values that determine layout and global inheritance.
function OnPreLayout(ctx)
    ctx.global.tracking = mt.wave(ctx.time, 0.25, 0.0) * 0.05
    ctx.global.rotation = mt.wave(ctx.time, 0.1, 0.0) * 5.0
end

-- Layout phase: adjust only the generated characters and parts.
function OnLayout(ctx)
    for index = 1, ctx.char_count do
        local character = ctx.chars[index]
        local progress = mt.stagger(ctx.time, index, 0.06, 0.35)
        character.offset_y = 0.5 + (1.0 - mt.ease.out_cubic(progress)) * 0.15
        character.rotation = character.rotation + mt.wave(ctx.time, 0.5, index * 0.25) * 3.0
    end

    for index = 1, ctx.part_count do
        local part = ctx.parts[index]
        part.scale = part.scale * (1.0 + mt.random(42, index) * 0.05)
    end
end

For more practical examples, see the bundled samples/. samples/reference/ contains short, numbered lessons for the scripting model and utilities, while samples/showcase/ is a collection of complete animation patterns.

4. Types and Coordinate Systems ​

4.1 Definitions of Coordinates and Units ​

Public number fields belong to one of the following unit systems.

X components use canvas width as 1, and Y components use canvas height as 1. Positive Y is upward (§4.3).

canvas normalized position ​

Represents a position on the canvas. The value 0.5 is the canvas center on the corresponding axis.

FieldDefinition
ctx.global.position_x / position_yGlobal position. Writable (OnPreLayout)
ctx.global.pivot_x / pivot_yDisplacement of the pivot for Global transformations relative to global.position. Writable (OnPreLayout)
canvas coordinates in geometry (bounds_center_*, etc.)Read-only positions in the pre-transformation layout. Different for each Character and Part

canvas normalized displacement (neutral value 0.5) ​

Represents displacement relative to the natural position determined by the layout. It is not an absolute position. The neutral value is 0.5, and the rendered displacement is interpreted as follows:

text
Displacement (canvas ratio) = value - 0.5

The displacement is based on canvas width or height, not character size or geometry.advance_*.

FieldDefinition
Character/Part offset_x / offset_yTranslation from the natural position. At 0.5, displacement is 0 and the item remains at the position determined by the layout (its center before transformations is geometry.bounds_center_*). Values greater than 0.5 translate right/up. Use mt.layout.place_2d to place an item at a target 2D canvas position
global.pivot_x / global.pivot_yDisplacement of the rotation/scale pivot from global.position. At 0.5, the pivot matches global.position

WARNING

shadow.distance is a percentage based on the canvas's shorter side. The lengths in bounding_box.* are percentages based on fontSize, so the bases differ even though both are percentages. If you write a value around 0.01 as though it used the same canvas ratio as offset_* or position_*, it actually becomes 0.01% of the shorter side (less than 1 px), and the shadow will not be visible. Multiply a canvas ratio by 100 to convert it (for example, use 1.2 for 1.2% of the shorter side). A practical range is approximately 0.8–2.0.

4.2 color ​

lua

r / g / b / a are numbers in the range 0–1. You do not need to specify all of r / g / b / a simultaneously. You can assign a partial table containing only the components to modify (for example, { a = 0.5 }). Properties for keys omitted during assignment retain the corresponding values from the original target color. Adding a key other than r / g / b / a causes an error.

4.3 Coordinates ​

  • See §4.1 for the unit definitions of position, offset, and pivot

  • X is based on canvas width, and Y is based on canvas height

  • For global.position, Character/Part offset / pivot, and geometry, positive Y is upward (increasing the Lua Y value moves upward on screen)

  • For 3D depth, positive z points deeper (larger values move farther from the camera and place the item deeper into the screen. Negative values move it closer to the viewer)

  • global.pivot and Character/Part offset / pivot are canvas normalized displacements (§4.1). Geometry canvas coordinates and global.position are canvas normalized positions

  • For geometry canvas positions, the lower-left of the canvas is 0,0, and the center is 0.5,0.5

  • Geometry local positions and advances are displacement amounts, so they have no center offset and are represented as Y-up

  • rotation, yaw, pitch, and angle are all in degrees

    • 2D rotation (rotation): Positive (+) is clockwise (right rotation), and negative (-) is counterclockwise (left rotation).
    • 3D object rotation (yaw, pitch): For both Individual and Global, rotation occurs around the individual pivot.
      • yaw: Positive (+) rotates the object's right edge toward the viewer (-Z) and its left edge deeper (+Z).
      • pitch: Positive (+) rotates the object's top edge toward the viewer (-Z) and its bottom edge deeper (+Z).
    • Camera orbit (yaw, pitch): The camera orbits around the look-at point.
      • yaw: Positive (+) moves the camera around to the right of the look-at point (the object on screen appears to rotate left).
      • pitch: Positive (+) moves the camera upward around the look-at point (producing a downward-looking angle).
    • Gradient angle (angle): At 0 degrees it progresses from left to right (positive X direction), and increasing (positive) angles rotate it clockwise.
    • Shadow angle (angle): At 0 degrees it extends rightward (positive X direction), and increasing (positive) angles rotate it clockwise (90 degrees points straight down).

WARNING

The 2D angle system consistently follows “screen intuition” (clockwise is positive, 90 degrees = straight down), which feels opposite to the coordinate system (Y-up). While positive offset_y points up, positive rotation / gradient.angle / shadow.angle rotates clockwise, and a shadow angle of 90 points straight down. Applying the mathematical Y-up convention (counterclockwise is positive, 270 = straight down) will cause mistakes such as shadows appearing directly above or rotations turning in the opposite direction.

When you turn an angle into a direction vector and feed it to offset_y, use mt.polar_offset_2d. Its input stays in the angle convention (90 degrees points down on screen), while the result uses the position convention (positive Y is upward), so it can be added directly to both offset_x and offset_y.

lua
local dx, dy = mt.polar_offset_2d(angle, radius)
character.offset_x = character.offset_x + dx
character.offset_y = character.offset_y + dy

TIP

Use mt.layout.radial_distance for distances in circular and radial effects. The canvas aspect ratio is corrected inside the function, so you do not need to transform the X coordinate manually.

lua
local distance = mt.layout.radial_distance(
    ctx,
    geometry.bounds_center_x,
    geometry.bounds_center_y
)

To calculate a signed distance or dot product in a diagonal direction, multiply the X difference by ctx.canvas.aspect_ratio before the calculation. Also multiply by ctx.canvas.pixel_aspect_ratio when accounting for the physical display ratio of non-square pixels.

pivot Is a Displacement from the Reference Point ​

  • ctx.global.pivot_x/y is a displacement from global.position. At 0.5, 0.5, the pivot matches global.position
  • Character/Part pivot_x/y is a displacement from the item's own reference point. At 0.5, 0.5, a Character rotates and scales around its natural bounding-box center (equivalent to geometry.bounds_center), while a Part rotates and scales around its natural position (equivalent to geometry.canvas_center)
  • Therefore, do not assign a canvas coordinate from geometry directly to a Character or Part pivot. To rotate around a point shifted 10% to the right from the item's own center, use pivot_x = 0.5 + 0.1
  • To use a Character's edge as its pivot, displace it from the natural center by half of its size (bounds_width / bounds_height are canvas-axis ratios and use the same unit system as pivot displacement):
    • Bottom edge: pivot_y = 0.5 - geometry.bounds_height * 0.5
    • Top edge: pivot_y = 0.5 + geometry.bounds_height * 0.5
    • Left edge: pivot_x = 0.5 - geometry.bounds_width * 0.5
    • Right edge: pivot_x = 0.5 + geometry.bounds_width * 0.5

4.4 Assignment Rules ​

Writable fields can be read and used in calculations with their current values.

lua
character.rotation = character.rotation + 10.0
character.fill.color.a = character.fill.color.a * 0.5

The following operations cause errors:

  • Assigning to a non-writable field
  • Adding an unknown field
  • Type mismatch (such as assigning a string where a number is expected)
  • Replacing or changing the number of elements in read-only containers such as ctx.chars / ctx.parts
  • Assigning an invalid string to an enumerated field

5. Inheritance Mechanism ​

Roles of use / opacity / fill.transparent ​

SettingEffect on rendering
fill.use / stroke.use / shadow.useWhen true, uses the individual values set on the target Character or Part; when false, inherits the parent settings. Does not toggle visibility
opacity (Global / Character / Part)Multiplies the opacity of the fill, stroke, shadow, and other values determined after inheritance. 0 is transparent, and 1 preserves the original opacity
global.fill.transparentMakes only the fill transparent. Does not affect the stroke or shadow

The color and opacity used for rendering are determined in the following order.

  1. Determine color: If fill.use is true, use the individual color set on the Character or Part; if false, use the gradient (when enabled) or the Global fill color
  2. Apply opacity: Multiply the opacity of the determined color by global.opacity × character.opacity × part.opacity

When use = false, modifying the individual color of a Character or Part does not make that color affect rendering. Changing only opacity changes only the opacity without changing the color or gradient being used.

Values used for rendering are determined in the following order.

text
Global finalized in OnPreLayout
  ↓
Character: if each group's use is true, use the Character's individual value; if false, use the Global value
  ↓
Part: if each group's use is true, use the Part's individual value; if false, use the value selected at the Character stage

When gradient.color_space is anything other than none, only the areas for which the Global value was selected in this order (where both the Character and Part fill.use values are false) are filled with the gradient. Characters or Parts with individual colors enabled are filled with their individual solid colors.

A Part's stroke / shadow follows the same order as fill when selecting the value to use, except that the host has no corresponding parameter groups for Parts (they always begin unused/with default values).

Characters and Parts passed to OnLayout contain individual settings before parent settings are applied. Lua can also modify the use field of each group, so an individual value can be modified and enabled within the same callback.

lua
local character = ctx.chars[index]
character.fill.use = true
character.fill.color = mt.color.from_hsv(index / ctx.char_count, 0.8, 1.0)

Transform fields (offset / scale / rotation, etc.) have no use_* field and always affect rendering. Script modifications are confined to that frame and are never written back to the host Inspector or keyframes.

6. Execution Environment, Errors, and Limits ​

6.1 Callback-Level Atomicity ​

If an error occurs anywhere in a callback, all changes made by that callback are discarded. Changes to only some Characters or assignments made before the error are never partially applied.

Failure locationResult
Script loadingThe entire script is not executed (the last valid script is not executed either)
OnInitializeReports the error and does not start frame evaluation for that script
OnPreLayoutRenders using values originating from the host and also skips OnLayout / OnPath
OnLayoutRenders the unmodified values generated from the finalized Global settings
OnPathRenders the original glyph outlines

6.2 Available Standard Libraries ​

The Lua standard libraries are limited to a safe subset.

  • Available: Safe basic functions, math, string, table, utf8
  • Unavailable: os, io, package, require, dofile, loadfile, load, debug, collectgarbage, rawget, rawset, getmetatable, setmetatable

Files, networks, and processes cannot be accessed.

6.3 Execution Limits ​

  • 5,000,000 instructions per callback invocation
  • Memory limit of 128 MiB (during host execution)

A callback that exceeds a limit is treated as failed and rolled back as described in §6.1.

6.4 print(...) ​

Lua's standard print(...) can be used to output diagnostic information to the Output panel in MT Sim. The host does not provide an output feature for end users, so calls are ignored there. It does not affect rendering values, but it is not intended to be called in large quantities within per-frame Character or Part loops.

6.5 Checking Errors ​

Script error details cannot be checked in the host. First run the script in MT Sim, then check and fix the error message and stack trace displayed in the Output panel.

Clip Range ​

The clip range is the clip's actual range on the timeline, including trimming and extensions before or after it. ctx.time, ctx.frame, and ctx.timeline receive values on the same time axis, with the beginning of the clip as 0. When applied to a video clip as a filter, they also follow that clip's range.

When available is false, the other values are 0, so provide a fallback.

NOTE

Limitation of extending the beginning in generator use: When the beginning of a generator clip (with no input connected) is extended on the timeline, the host treats that interval as a still image of the first frame, so script time does not advance until the extension boundary (the intro appears frozen in its initial state). To change the duration, change the length of the generator clip itself instead of extending it. This limitation does not apply when used as a filter.

Time-Axis Design Rules (Anchor × Speed) ​

Animation timing is designed along 2 axes: "① where it is fixed (anchor)" and "② how fast it advances (speed)." The default speed is real seconds (based on ctx.time), and progress, which scales proportionally with clip length, should be used only for the "full-span" pattern described below.

PatternAnchorHow to Write It

Typewriter, stagger, spring, etc.Beginning of clipctx.time (real seconds; specify a physical speed such as ◯ seconds per 1 character)
Full-span pattern (drift, sweep, or reveal across the entire duration)Entire clipprogress (the expected behavior is for the movement to lengthen when the duration is extended)

If a transition is written as a fraction of progress, extending the clip makes the fade or typing run in slow motion and breaks the intended behavior. An outro is fundamentally about aligning with the end rather than making its speed proportional to the duration, so write it in real seconds anchored to the end.

-- NG: typing speed changes when the clip length changes
local visible = math.floor(mt.timeline.progress(ctx) * ctx.char_count)

-- OK: constant 0.08s per character regardless of clip length

-- OK: outro fade over the last 0.5s, anchored to the clip end
local fade = mt.clamp(mt.timeline.remaining(ctx) / 0.5, 0.0, 1.0)

-- OK: 0.8s intro + 0.5s outro at fixed real-time speed
-- (compressed automatically only when the clip is shorter)

mt.friction_decay(t, speed, friction) ​

API level: 3+

Calculates exponential deceleration caused by friction. It lets you control motion that “rushes in and glides to a stop” using the physical quantities initial velocity and coefficient of friction, rather than arrival time.

Arguments ​

ArgumentTypeUnitDefaultDescription
tnumbersecondsRequiredElapsed time. Negative values are treated as 0

Return Value ​

TypeUnitDescription

numbercanvas normalized displacement/secondcurrentSpeed. Speed at that time

The final travel distance converges to speed / friction. Conversely, if the stopping distance is known, you can set speed = distance * friction.

Choosing between it and mt.ease.out_expo: easing represents progress from 0→1 over a fixed duration, whereas this function treats initial velocity and friction as independent physical quantities. Example ​

lua
-- Slide in from the left and stop through friction

NOTE

When friction is extremely small (1e-4 or less), motion is treated as uniform linear motion. This avoids numerical cancellation and is effectively equivalent to frictionless motion in practical use.

mt.layout.queue_on_path(ctx, path, options?) ​

API level: 3+

Arranges characters (or parts) on a path created by mt.path.arc_length in reading order, and returns the distance ratio (0–1) occupied by each element.

Spacing is derived from the origin spacing that the host actually typeset, using the same method as mt.layout.reflow. Parameter settings such as tracking, per-character margins, and kerning are therefore reflected directly in the character advance along the path. options.gap is additional spacing added on top of that, so when gap is 0, elements are arranged according to the host’s character advance.

Arguments ​

ArgumentTypeUnitDefaultDescription
ctxtable—RequiredOnLayout context
pathtable—RequiredReturn value of mt.path.arc_length
optionstable—nilPlacement settings
options.alignstring—"end"Position at which to place the string. Specify "end", "start", or "center"
options.gapnumberRatio of canvas width0.0Additional spacing added to the host’s character advance
options.modestring—"horizontal"Host typesetting direction: "horizontal" or "vertical"
options.target_typestring—"character"Target type: "character" or "part"
options.targetstable—All elementsArray of target indices in reading order

Return Value ​

TypeUnitDescription
table0–1slots array indexed like ctx.chars or ctx.parts, providing the distance ratio occupied by each element on the path

slots represents positions on the path, not animation progress.

Direction of Travel and Reading Order ​

Slots are assigned in ascending distance along the direction of travel. The reference is the path’s direction, not left and right on the screen. If targets is omitted, slots are assigned by ascending index; therefore, if the path travels from left to right, this directly produces screen reading order.

IMPORTANT

On a path traveling from right to left, ascending distance corresponds to decreasing x. Therefore, when targets is omitted, character 1 is placed farthest right and character N farthest left, making the string appear reversed on screen. To produce a left-to-right-readable arrangement, pass targets in reverse reading order.

lua
-- Preserve screen reading order on a path traveling from right to left
local targets = {}
for index = ctx.char_count, 1, -1 do
    targets[#targets + 1] = index
end
local slots = mt.layout.queue_on_path(ctx, path, { targets = targets })

This is a tradeoff: the following two properties cannot both be satisfied on a reversed path. Choose according to the use case.

targetsOn-Screen ArrangementFront of the Queue
Omitted (ascending index)Reversed (read right→left)Character 1
Reverse reading orderCorrect (read left→right)Last character

align is likewise relative to the direction of travel. "end" places the end of the string at the end of the path, so on a path traveling right to left, the end of the string appears on the left side of the screen.

Path DirectionPosition of the String End with align = "end"
Left→rightRight side of the screen
Right→leftLeft side of the screen

Example ​

lua
-- Use case 1: Arrange text along a path (stationary)
local path = mt.path.arc_length(kPathPoints, ctx.canvas.aspect_ratio)
local slots = mt.layout.queue_on_path(ctx, path, { gap = 0.004 })
for index = 1, ctx.char_count do
    local x, y, heading = path:at_distance(slots[index])
    ctx.chars[index].rotation = heading
    mt.layout.place_2d(ctx, ctx.chars[index], x, y)
end
lua
-- Use case 2: Travel along the path and stop at each character's own slot (the queue brakes)
local path = mt.path.arc_length(kPathPoints, ctx.canvas.aspect_ratio)
local slots = mt.layout.queue_on_path(ctx, path, { align = "end" })
local progress = mt.ease.out_cubic(mt.saturate(ctx.time / 3.2))
for index = 1, ctx.char_count do
    -- math.min implements the queue's stopping behavior itself: the leader reaches the end, while each follower stops at its own position
    local x, y, heading = path:at_distance(math.min(progress, slots[index]))
    ctx.chars[index].rotation = heading
    mt.layout.place_2d(ctx, ctx.chars[index], x, y)
end

NOTE

If the string’s total length exceeds the path length, distance ratios are clamped to 0 and 1, causing characters to overlap. When placing long text on a short path, use path:length() to confirm that it fits.

15. Motion Paths ​

These curve-evaluation APIs represent motion along control points, such as “flowing in” or “landing along an arc.”

The coordinate system is not fixed. Points are plain { x, y } tables. The functions accept whichever coordinate system the caller passes, such as normalized offset coordinates, canvas pixels, or character-local coordinates, and return values in the same coordinate system.

NOTE

When assigning returned values directly to offset_x / offset_y, specify the points in offset units as well (the canvas normalized displacement whose neutral value is 0.5). In the example below, the landing point is { x = 0.5, y = 0.5 } (zero displacement), so character.offset_x = x lands directly at the natural position. If absolute canvas coordinates or zero-based local coordinates are assigned to offset unchanged, the character will move to an unintended position.

Every function returns four values: x, y, tangentX, tangentY. tangentX / tangentY are raw, unnormalized derivatives that also include travel speed. To obtain the direction angle, use math.deg(math.atan(tangentY, tangentX)); to obtain a unit vector, divide by local length = math.sqrt(tangentX^2 + tangentY^2).

mt.path.arc_length(points, aspectRatio?, options?) ​

API level: 3+

Constructs an arc-length-parameterized path from control points. The two functions above evaluate using curve parameter t, but equal intervals of t are not equal distances. Samples bunch together where the curve bends, so uses that require spacing by distance, such as queues, character advance along a path, or constant-speed motion, require a cumulative-length table. This function constructs that table once and provides distance-based lookup.

Passing ctx.canvas.aspect_ratio as aspectRatio multiplies X differences by it to equalize the meaning of distance on the horizontal and vertical axes. If omitted, distance is measured directly in normalized units, causing spacing to expand or contract on a non-square canvas.

Arguments ​

MethodReturn ValueUnitDescription

  • points must contain at least two points.
  • With options.kind = "bezier", points must contain exactly four points.

    local x, y, heading = path:at_distance(ratio)
    ctx.chars[index].rotation = heading
    mt.layout.place_2d(ctx, ctx.chars[index], x, y)
end

Each interval uses one of the following forms.

IntervalSpecificationBehavior
Fixed-length animation{ duration = seconds, evaluate = function }Uses the return value of evaluate(segmentCtx, previousValue)
Fixed-length hold{ hold = seconds }Retains the preceding value without calling a function
Variable-length animation{ duration = "remaining", evaluate = function }Uses the remaining clip duration after fixed intervals are excluded

lua
local state = mt.timeline.chain(ctx, initialState, {
    { duration = 1.0, evaluate = evaluateIntro },
    { duration = 1.2, evaluate = evaluateBounce },
    { duration = "remaining", evaluate = evaluateIdle },
    { duration = 0.6, evaluate = evaluateOutro },
}, {
    fallback_duration = 6.0,
})

If the total length of fixed intervals exceeds the clip length, all fixed intervals are compressed proportionally. Because segmentCtx.time and segmentCtx.timeline are remapped to the declared duration, every animation reaches its ending state even in a short clip. When the timeline is unavailable, options.fallback_duration (default 4.0 seconds) is used as a virtual looping clip length.

Constraints and Errors ​

  • ctx.time must be a number, and segments and options must be tables.
  • Each interval must specify exactly one of duration or hold.
  • A duration interval requires an evaluate function, which cannot be specified for a hold interval.
  • An interval length must be a finite number greater than or equal to 0, or "remaining".
  • Only one interval may specify "remaining".
  • options.fallback_duration must be a finite positive number.

IMPORTANT

evaluate is reevaluated within the same frame to obtain the ending values of past intervals. Write it as a pure function that returns a value calculated from its arguments without directly modifying ctx or a character, and apply only the final result. Combine value-returning APIs such as mt.bounce_y with segmentCtx.time, rather than using APIs such as mt.bounce_ground that modify an item directly.

This appendix explains issues that can be confusing when creating scripts and how to address them.

1. Adjusting the advance of individually scaled characters ​

1.1 When this is needed ​

This is needed when you change scale or stretch for individual characters in OnLayout and want to rearrange the characters according to their resulting sizes.

1.2 The problem ​

Character advances are determined before individual transformations are applied in OnLayout. Therefore, simply changing scale or stretch for each character can cause the following problems.

  • Enlarged characters overlap adjacent characters.
  • Extra spacing remains on both sides of reduced characters.
  • Character reference positions shift away from the baseline.

This occurs because characters are scaled up or down around geometry.bounds_center while their original advances remain unchanged.

1.3 Solution ​

After changing character size, rotation, and pivot, call mt.layout.reflow at the end of OnLayout.

lua
function OnLayout(ctx)
    for index = 1, ctx.char_count do
        local character = ctx.chars[index]
        character.scale = 0.8 + index * 0.05
    end

    -- Adjust advances to match the character sizes after transformation
    mt.layout.reflow(ctx)
end

If you need additional space between characters, specify the spacing in the second argument. To limit the affected characters or the characters that remain fixed, specify config. For argument details, see mt.layout.reflow.

1.4 How it works ​

mt.layout.reflow uses the horizontal and vertical layout origins to rearrange characters according to their current scale, stretch, rotation, and pivot while preserving the spacing produced by shaping, kerning, tracking, and margins. It does not make the spacing between individual ink outlines uniform.

When the pivot is 0.5 and only scale is changed, a point P in natural coordinates moves according to the following formula. C is geometry.bounds_center, s is scale × stretch, and d is offset − 0.5.

text
P' = C + s × (P − C) + d
d  = P'(target) − C − s × (P − C)

You do not need to calculate this formula directly in the script. mt.layout.reflow aligns the layout origins while accounting for the complete 2D character transformation, including rotation, pivot, vertical writing, and non-square canvases.

2. Adjusting the gradient range and direction ​

2.1 When this is needed ​

Check this section when the gradient start position, end position, or color direction does not match your expectations after changing start_position, end_position, or angle.

2.2 The problem ​

start_position and end_position are not coordinates relative to the entire canvas. The gradient angle is also not calculated using only the width or height of the bounding box.

If you treat these values as canvas coordinates, the position where the colors transition may appear to shift away from the expected location when the text is moved, rotated, or enlarged, or when a diagonal gradient is set.

2.3 Solution ​

Specify start_position and end_position as ratios of the range of the entire transformed text as viewed along the angle direction.

  • To apply the gradient from one edge of the text to the other, set start_position = 0.0 and end_position = 1.0.
  • To transition colors inside the text, increase start_position and decrease end_position. With the standard settings of 0.2 and 0.8, the gradient interval begins 20% inward from each edge.
  • With angle = 0, colors change from left to right; with angle = 90, from top to bottom; and with angle = -90 or 270, from bottom to top.

The fill color is assigned to the start_position side, and end_color is assigned to the end_position side. The direction of angle follows the same definition as coordinates.

2.4 Reference range ​

The gradient uses the bounding box of the entire text after scale, rotation, offset, and other transformations have been applied to characters and parts in OnLayout.

  • During 2D rendering: This is the 2D bounding box on the canvas that encloses the transformed paths of all characters and parts.
  • During 3D projection: This is the bounding box on the 3D layout plane, unaffected by camera projection. Because projected coordinates are calculated for each character, the gradient position does not shift relative to the characters when the camera moves.

2.5 How the reference line is calculated ​

The gradient reference line from 0.0 to 1.0 is the line segment connecting the nearest and farthest extents when the bounding box is projected in the angle direction. For diagonal directions, the boundaries are not based on the rectangle's width or height, but on the position that extends farthest in the specified direction and the position on the opposite side.

Let the center of the bounding box be $C$, the direction vector of angle be $D$, and the four vertices be $P_i$. The projected value of each vertex is calculated using the following formula.

$$\text{proj}_i = (P_i - C) \cdot D$$

If the minimum projected value is $\text{minProj}$ and the maximum projected value is $\text{maxProj}$, the start point bbP0 and end point bbP1 of the reference line are as follows.

$$\text{bbP0} = C + D \cdot \text{minProj}$$ $$\text{bbP1} = C + D \cdot \text{maxProj}$$

If start_position is $t_s$ and end_position is $t_e$, the actual start point P0 and end point P1 are the following positions on the reference line.

$$\text{P0} = \text{bbP0} + (\text{bbP1} - \text{bbP0}) \cdot t_s$$ $$\text{P1} = \text{bbP0} + (\text{bbP1} - \text{bbP0}) \cdot t_e$$

3. Passing values between callbacks ​

3.1 When this is needed ​

This is needed when you want to use a value from before it is overridden in OnPreLayout later in OnLayout during the same frame. For example, this applies when using the host's Scale as a factor that determines animation travel rather than character size.

3.2 The problem ​

If you change ctx.global.scale to 1.0 in OnPreLayout, OnLayout can only access the modified value. Because the original host value cannot be restored, you can no longer perform calculations using that value.

In contrast, values that are not overridden in OnPreLayout can be read directly from ctx.global in OnLayout. For example, reference tracking and line_spacing directly where they are used instead of saving them.

3.3 Solution ​

Save the value before it is overridden in a local variable declared outside the functions, and reference it from OnLayout. One Lua execution environment is created for each instance and persists until the script is reloaded, so the same variable can be referenced across callbacks.

lua
local scaleKnob = 1.0

function OnPreLayout(ctx)
    -- Save the host's Scale, then cancel its effect on character size
    scaleKnob = math.max(ctx.global.scale, 0.05)
    ctx.global.scale = 1.0
end

function OnLayout(ctx)
    local travel = 0.07 * scaleKnob
    for index = 1, ctx.char_count do
        ctx.chars[index].offset_y = ctx.chars[index].offset_y + travel
    end
end

Use this method only when you need a value from before it was overridden. Saving unnecessary values increases the script's state and makes the flow of processing harder to understand. See 56_inspector_knobs.lua for a practical example.

3.4 Do not use this to preserve state between frames ​

Variables declared outside functions retain their values not only between callbacks but also between frames. However, due to seeking, changes in rendering order, parallel rendering, and other factors, the host does not necessarily evaluate frames in chronological order.

If you perform delta calculations or accumulation using values from the previous frame, the results may differ between playback and rendering. Ensure that the result of each frame is determined uniquely from that frame's ctx.time. Outside functions, retain only constants and values passed between callbacks within the same frame.

NOTE

OnInitialize and mt.storage are retained for compatibility with existing scripts. Do not use them in new scripts.
